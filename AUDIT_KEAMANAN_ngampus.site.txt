───────────────────────────────────────────────────────────
[NGAMPUS-01] SEDANG — Tidak ada rate limiting pada auth
───────────────────────────────────────────────────────────
CVSS 3.1: 5.3 (Medium)

Lokasi: POST /auth/v1/token?grant_type=password
        (endpoint Supabase Auth yang dipakai form login)

Deskripsi:
Tidak ada pembatasan jumlah percobaan login. Diuji 40 kali
percobaan login gagal berturut-turut dalam ~1 menit: SEMUA
mengembalikan HTTP 400 "Invalid login credentials", tanpa
satu pun HTTP 429 (Too Many Requests) dan tanpa header
Retry-After.

Bukti:
  [1]  HTTP 400  Invalid login credentials
  [5]  HTTP 400  Invalid login credentials
  ...
  [40] HTTP 400  Invalid login credentials
  -> Tidak ada rate limit sampai 40 percobaan

Sebagai perbandingan, sistem lain yang diuji (matchu.id)
mengembalikan HTTP 429 setelah 5 percobaan gagal.

Dampak:
- Brute-force password memungkinkan (terutama password lemah
  yang masih diizinkan minimal 6 karakter)
- Credential stuffing (uji daftar email:password bocor dari
  kebocoran situs lain) bisa dijalankan tanpa hambatan
- Akun mahasiswa berisi data akademik, jadwal, dan catatan
  pribadi — target yang bernilai

Rekomendasi:
- Aktifkan rate limiting di Supabase: Dashboard > Authentication
  > Rate Limits (atur "Sign in / sign up" dan "Token refresh")
- Tambahkan rate limiting per-IP DAN per-akun di level aplikasi
- Terapkan exponential backoff / CAPTCHA setelah 3-5 gagal
- Pertimbangkan proteksi tambahan (Vercel WAF / Cloudflare)

───────────────────────────────────────────────────────────
[NGAMPUS-02] SEDANG — Registrasi tanpa verifikasi email
───────────────────────────────────────────────────────────
CVSS 3.1: 5.3 (Medium)

Lokasi: GET /auth/v1/settings (konfigurasi terekspos publik)

Deskripsi:
Konfigurasi Supabase Auth menunjukkan:
  mailer_autoconfirm : true    <- konfirmasi email NONAKTIF
  disable_signup     : false   <- pendaftaran terbuka

Artinya: siapa pun dapat mendaftar memakai alamat email APA PUN
tanpa perlu membuktikan kepemilikan email tersebut.

Bukti:
  GET https://cuozkidsrhphkqsyupyv.supabase.co/auth/v1/settings
  -> "mailer_autoconfirm": true, "disable_signup": false

Dampak:
- Akun spam / pembuatan akun massal tanpa hambatan
- Jika ada alur "lupa password" berbasis email, seseorang bisa
  mendaftar memakai email orang lain lebih dulu. Ketika pemilik
  email asli mencoba mendaftar atau reset, akun tersebut sudah
  diklaim pihak lain (risiko pengambilalihan identitas akun)
- Data akademik yang dilaporkan menjadi tidak dapat dipercaya

Rekomendasi:
- Aktifkan "Confirm email" di Supabase Auth settings
  (set mailer_autoconfirm = false)
- Tambahkan verifikasi email institusi untuk fitur tertentu
- Pertimbangkan pembatasan domain email (.ac.id) bila relevan

───────────────────────────────────────────────────────────
[NGAMPUS-03] SEDANG — Tidak ada SPF, DMARC, dan CAA
───────────────────────────────────────────────────────────
CVSS 3.1: 5.0 (Medium)

Lokasi: DNS zone ngampus.site (dikelola Hostinger)

Deskripsi:
Tidak ditemukan record keamanan email dan sertifikat:
  TXT  ngampus.site          -> TIDAK ADA (tanpa SPF)
  TXT  _dmarc.ngampus.site   -> TIDAK ADA (tanpa DMARC)
  CAA  ngampus.site          -> TIDAK ADA

Bukti (via Google DoH):
  dns.google/resolve?name=ngampus.site&type=TXT   -> kosong
  dns.google/resolve?name=_dmarc.ngampus.site&type=TXT -> kosong
  dns.google/resolve?name=ngampus.site&type=CAA   -> kosong

Dampak:
- Tanpa SPF + DMARC: siapa pun dapat mengirim email yang
  tampak berasal dari @ngampus.site. Sangat efektif untuk
  phishing ke mahasiswa ("reset password", "pengumuman
  akademik") — kredensial bisa dicuri.
- Tanpa CAA: otoritas sertifikat mana pun dapat menerbitkan
  sertifikat TLS untuk domain ini tanpa otorisasi.

Rekomendasi:
- Tambahkan SPF, mis.:
    TXT @ "v=spf1 include:<provider-email> ~all"
- Tambahkan DMARC bertahap:
    TXT _dmarc "v=DMARC1; p=none; rua=mailto:dmarc@ngampus.site"
    lalu naikkan ke p=quarantine, lalu p=reject
- Tambahkan CAA, mis.:
    CAA @ 0 issue "letsencrypt.org"
- Aktifkan DKIM di penyedia email yang dipakai

───────────────────────────────────────────────────────────
[NGAMPUS-04] RENDAH — CSP melemahkan proteksi XSS
───────────────────────────────────────────────────────────
CVSS 3.1: 3.1 (Low)

Deskripsi:
Content-Security-Policy memuat 'unsafe-eval' dan 'unsafe-inline'
pada script-src:
  script-src 'self' 'unsafe-eval' 'unsafe-inline';
  script-src-elem 'self' 'unsafe-inline'

Dampak:
Bila ada celah injeksi HTML (mis. rendering nama pengguna tanpa
escaping), script penyerang bisa dieksekusi. CSP yang ketat
seharusnya menjadi jaring pengaman terakhir — di sini jaring itu
tidak berfungsi untuk skenario tersebut.

Catatan: bagian CSP lain sudah sangat baik (object-src 'none',
base-uri 'self', form-action 'self', frame-ancestors 'none').

Rekomendasi:
- Ganti 'unsafe-inline' dengan nonce atau hash
- Hilangkan 'unsafe-eval' bila tidak diperlukan (biasanya hanya
  dibutuhkan beberapa pustaka tertentu)
- Uji dengan CSP Report-Only sebelum diterapkan penuh

───────────────────────────────────────────────────────────
[NGAMPUS-05] RENDAH — COEP/CORP tidak diterapkan
───────────────────────────────────────────────────────────
CVSS 3.1: 2.6 (Low)

Deskripsi:
Header Cross-Origin-Embedder-Policy dan
Cross-Origin-Resource-Policy tidak ada.

Dampak:
Kurang pertahanan terhadap serangan XS-Leaks (kebocoran
informasi lintas-origin melalui timing/side-channel).

Rekomendasi:
- Tambahkan Cross-Origin-Resource-Policy: same-origin
- Pertimbangkan Cross-Origin-Embedder-Policy: require-corp
  (uji dampaknya ke gambar/iframe pihak ketiga lebih dulu)

───────────────────────────────────────────────────────────
[NGAMPUS-06] RENDAH — Timeout idle dapat diubah dari klien
───────────────────────────────────────────────────────────
CVSS 3.1: 3.1 (Low)

Deskripsi:
Auto-logout idle membaca konfigurasi dari localStorage:
  localStorage.getItem("ngampus_idle_timeout_mins") || 30

Dampak:
Sesi tidak benar-benar dipaksa berakhir oleh server. Di komputer
bersama (lab kampus, warnet, kos), pengguna bisa mengubah nilai
ini agar sesi tetap terbuka jauh lebih lama — berisiko bila
perangkat ditinggalkan.

Rekomendasi:
- Terapkan batas sesi dari sisi server (Supabase JWT expiry)
- Jangan bergantung pada nilai konfigurasi yang bisa diubah klien
- Pertimbangkan batas absolut sesi (mis. wajib login ulang
  setiap 12 jam) untuk data akademik

───────────────────────────────────────────────────────────
[NGAMPUS-08] INFORMASIONAL — Inkonsistensi minimal password
───────────────────────────────────────────────────────────
Deskripsi:
UI menampilkan "Minimal 8 karakter", namun Supabase Auth
menolak dengan ambang 6 karakter:
  -> 422 "Password should be at least 6 characters."

Dampak:
Validasi sebenarnya bergantung pada server. Password 6 karakter
tetap dapat dibuat lewat pemanggilan API langsung (melewati UI),
memperkuat dampak NGAMPUS-01.

Rekomendasi:
- Samakan ambang minimal password di Supabase Auth settings
  dengan yang ditampilkan UI (minimal 8), dan aktifkan
  pemeriksaan password lemah / bocor
